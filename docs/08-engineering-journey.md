# The Engineering Journey

> **TenantWall was built by solving hard problems the right way. This section documents what didn't work — because the lessons are as valuable as the code.**

---

## Attempt 1: `Connection.prepareStatement` interception (FAILED)

**Approach:** Intercept the JDBC entry point directly.

**What we saw:**

- Logs showed `Modified SQL: SELECT ... WHERE tenant_id = 'X'`
- MySQL general log showed `SELECT ...` (no `WHERE`)

> [!CAUTION]
> **Root cause:** HikariCP generates `HikariProxyConnection` via **Javassist at runtime**. ByteBuddy's `@Advice.AllArguments(readOnly=false)` writes back to the arguments array, but **Javassist-generated bytecode doesn't propagate the mutation** to the actual method parameters.

**Lesson:** `@Advice.AllArguments(readOnly=false)` cannot be trusted across proxy boundaries.

---

## Attempt 2: `Statement.executeQuery` interception (PARTIAL)

**Approach:** Intercept at the `Statement` level.

**What we saw:** `JdbcTemplate` queries worked, but **Hibernate queries bypassed it** — Hibernate uses `PreparedStatement`, not `Statement`.

**Lesson:** JDBC layer has multiple interception points; each covers a different code path.

---

## Attempt 3: `StatementPreparerImpl.prepareQueryStatement` interception (SUCCESS)

**Approach:** Intercept at Hibernate's SQL generation layer — **before** it reaches HikariCP.

**Why it worked:**

1. `StatementPreparerImpl` is a **regular Java class** (not Javassist-generated)
2. ByteBuddy `@Advice.Argument(0, readOnly=false)` modifies the argument slot directly
3. The modified SQL reaches `HikariProxyConnection` **already rewritten**

**Verification:**

- MySQL general log confirmed `WHERE p1_0.tenant_id = 'SHOP_ALPHA'` reached the database
- Cross-tenant GET/PUT/DELETE returned 404 as expected
- 88/88 tests passed across 3 databases

> [!TIP]
> **The Insight:** Intercept at the highest layer where classes are stable. Hibernate's SPI is more reliable than JDBC's driver-proxy layer.

## Additional Lessons

| Problem | Solution |
|---|---|
| `tenant_id` ambiguous in JOIN | Alias-prefix extraction from `PlainSelect.getFromItem()` |
| CTE bodies not filtered | `processWithItems()` in `SelectHandler` |
| `INSERT INTO t VALUES (...)` without columns | `TableSchemaProvider` SPI (Noop / Properties / Custom) |
| Python parser 404 (trailing slash) | URL normalization in `PythonServiceClient` |
| Hibernate lazy-load JSON 500 | DTO projection + `@Transactional` |
| Emoji / UTF-8 garbling on Windows | `chcp 65001` + `System.err` for diagnostic logs |
| MSSQL `Cannot open database` | Manual `CREATE DATABASE` (unlike MySQL) |
| Oracle no auto-commit on `data.sql` | Explicit `COMMIT;` at end |
| Git Bash path conversion (`/opt/...` → `C:/Program Files/Git/opt/...`) | `MSYS_NO_PATHCONV=1` |
| MSSQL `IDENTITY` inserts | `SET IDENTITY_INSERT ON/OFF` |
| Oracle user = schema | `APP_USER` in Docker = schema name |
| Spring Boot MSSQL driver + TLS | `encrypt=false;trustServerCertificate=true` |
| `args[0] = modifiedSql` not propagating | `@Advice.Argument(0, readOnly=false)` (not `@AllArguments`) |
| Cache not invalidated on config change | `setFilterColumn()` clears cache automatically |

## The Debugging Trail

Each bug took hours to diagnose. The pattern was always:

1. **Log said one thing** (`Modified SQL: ...`)
2. **Database received another** (`SELECT ...` without `WHERE`)
3. **The gap between them** was where the bug lived

### Example: The `readOnly = false` Investigation

**The bug:** Logs confirmed SQL rewrite, but the DB got the original.

**Investigation steps:**

1. **Confirmed SQL was modified** (agent logs)
2. **Confirmed DB got original** (MySQL general log)
3. **Checked ByteBuddy bytecode** (javap on transformed class)
4. **Read ByteBuddy docs** (found the `AllArguments` caveat)
5. **Tested with `@Advice.Argument`** (worked immediately)
6. **Tested across HikariCP + Javassist proxies** (confirmed root cause)

**Time to fix:** 30 seconds (change one annotation).
**Time to diagnose:** 6+ hours.

## Key Design Decisions

### Why JSqlParser?

- **Mature** — 10+ years, 3K+ GitHub stars
- **Pure Java** — no external runtime
- **Small footprint** — 300KB (after shading)
- **Handles 90% of queries** — most SaaS apps use simple SQL

**Alternatives considered:**

- **Calcite** — too heavy (25MB+)
- **Presto parser** — not standalone
- **ANTLR-based** — more work, less coverage

### Why Python `sqlglot` for complex SQL?

- **Best-in-class** dialect support (10 dialects)
- **Handles CTEs, window functions, recursive queries** (JSqlParser struggles)
- **Actively maintained** (weekly releases)
- **Small Python dependency**

**Alternatives considered:**

- **Apache Calcite** (Java) — heavy, complex API
- **JSqlParser only** — fails on some CTEs
- **Custom parser** — 6+ months of work

### Why Caffeine cache?

- **Fastest Java cache** (benchmarks)
- **No dependencies**
- **Window-TinyLFU eviction** (better than LRU)
- **Built-in stats** (`hitCount`, `missCount`, `evictionCount`)

## What We Didn't Do (And Why)

| Idea | Why Not |
|---|---|
| **Rewrite SQL at proxy layer** | Too late — Hibernate already cached PreparedStatement |
| **Use `StatementInspector`** | Requires app code changes — breaks "zero-code" promise |
| **Use Hibernate `@TenantId`** | ORM-only, doesn't cover native SQL |
| **Use native RLS** | DB-specific, requires DBA |
| **Build a custom SQL parser** | 6+ months, reinventing JSqlParser |
| **Ship a fat jar with Python bundled** | 400MB+ size, defeats lightweight agent goal |

## Why This Matters

Most multi-tenancy libraries fail because:

- **"Works in tests, fails in production"** — missing edge cases
- **"Works for some queries"** — ORM-only, native-only
- **"Requires massive refactor"** — breaks existing apps

**TenantWall took the hard path:**

- Multiple failed attempts before the breakthrough
- Full integration tests on 3 databases
- Real cross-tenant security verification

**The result:** a library that actually works in production.
